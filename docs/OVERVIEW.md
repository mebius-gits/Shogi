# 櫻間 Shogi 功能與技術說明

本文件整理四件事：**支援設備**、**玩法**、**電腦對手（機器人）使用的技術**、**MQTT 連線使用的技術**。安裝、操作與規則細節請見 [README.md](../README.md)。

---

## 1. 支援設備

### 1.1 架設端（開伺服器的電腦）

| 項目 | 需求 |
| --- | --- |
| 作業系統 | 任何能執行 Node.js 的系統（Windows／macOS／Linux）。Windows 可直接雙擊 `launch.cmd` |
| 執行環境 | Node.js（`scripts/server.mjs` 只用內建模組，**不需要 `npm install`**） |
| 網路 | 單機遊玩不需網路；連線對戰需能連到 MQTT broker |

`scripts/server.mjs` 只是靜態檔案伺服器，不處理任何遊戲邏輯。預設只聽 `127.0.0.1:4174`；設定 `HOST=0.0.0.0` 後，同一個區域網路的手機、平板也能用瀏覽器開啟。

### 1.2 遊玩端（瀏覽器）

遊戲是純前端網頁，桌機、筆電、平板、手機都能玩，只要瀏覽器支援以下功能：

| 瀏覽器功能 | 用途 |
| --- | --- |
| WebGL | Three.js 繪製 3D 棋盤、棋子、和服手與陰影 |
| ES Modules、Module Web Worker | 載入程式模組；電腦思考在背景執行緒 |
| WebSocket | MQTT 連線對戰 |
| Web Audio | 落子音效（載入失敗時改用合成音） |
| `crypto.getRandomValues` | 產生房號與連線 ID |
| localStorage | 保存玩家資料、偏好與上次的選項 |

新版 Chrome、Edge、Safari、Firefox 都具備這些功能。**實際自動化測試使用的是 Microsoft Edge（Chromium）**，其他瀏覽器沒有逐一驗證。

### 1.3 螢幕與輸入

| 螢幕寬度 | 排版 |
| --- | --- |
| 大於 1100px（桌機、筆電） | 三欄：左側棋譜、中間棋盤、右側資訊 |
| 1100px 以下（平板、小視窗） | 棋盤居中，兩側名牌，棋譜與操作列移到下方 |
| 650px 以下（手機） | 棋盤佔滿寬度，名牌改為棋盤上下的細長列；棋盤與雙方名牌在一個畫面內。首頁選單不需捲動即可看到全部 |

- 瀏覽器測試涵蓋 1440×1000、1280×900、390×844（手機）、320×720（小手機）等視窗尺寸。
- **輸入**：滑鼠點擊、觸控點按；鍵盤可用 Tab 聚焦棋盤格、方向鍵移動、Enter／空白鍵選取、Escape 取消。
- **效能**：畫面解析度倍率上限為 2；較慢的裝置可在設定中關閉陰影與動畫。系統開啟「減少動態效果」時會自動套用。

## 2. 玩法

### 2.1 三種模式

| | 電腦對戰 | 連線對戰 | 同機雙人 |
| --- | --- | --- | --- |
| 對手 | 電腦角色「花咲 小春」 | 另一台裝置的玩家（MQTT） | 同一台裝置輪流下 |
| 棋力選擇 | 入門／中級／高級 | — | — |
| 先後手 | 先手／後手／隨機 | 房主選先手／後手／隨機；隨機配對一律隨機 | 固定 |
| 提示・悔棋・暫停 | ✓ | — | ✓ |
| 入玉宣言・投了 | ✓ | ✓ | ✓ |
| 後手時棋盤翻轉 | ✓ | ✓ | — |
| 再來一局 | ✓ | ✓（雙方同意後交換先後手） | ✓ |

### 2.2 用時

- 無限時
- 5 分鐘＋每手 10 秒讀秒
- 10 分鐘＋每手 30 秒讀秒

主時間用完進入讀秒，每手讀秒重設；落子動畫期間不扣時。電腦與同機對局在切到其他分頁或開啟設定時會自動暫停。

### 2.3 規則

完整的平手將棋規則，由 `src/rules/engine.js` 執行：

- 八種基本棋子與六種成駒、取子、持駒打入、升變（可選成／不成，末段強制升變）。
- 自動阻止禁手：二步、打步詰、無處可走的打入、自陷王手。
- 終局判定：將死、投了、時間到、千日手、連續王手千日手、入玉宣言（業餘 27 點制）、500 手持將棋，連線對戰另有斷線判定。

### 2.4 其他功能

- 終局後可逐手回顧，也能下載 KIF 棋譜。
- 自訂玩家名稱與頭像。
- 春日／夕暮（預設）／月夜三種光線，和服手的落子動畫。

## 3. 電腦對手（機器人）使用的技術

電腦對手是自行撰寫的**傳統搜尋型將棋引擎**（`src/ai/ai.js`），不使用類神經網路、雲端服務或外部 API，完全在玩家的瀏覽器裡計算。

### 3.1 架構

```
app.js ──postMessage(局面, 深度, 時限, 本局歷史局面)──▶ ai-worker.js（Web Worker）
   ▲                                                      │ chooseMove()
   └───────────────── postMessage(最佳著手) ◀──────────────┘
```

- **Web Worker 背景執行**：搜尋在獨立執行緒進行，電腦思考時畫面與動畫不會卡頓。
- **可中斷**：每次思考都建新的 Worker 並帶上工作編號；玩家悔棋、暫停或離開時直接 `terminate()`，過期的結果依編號丟棄。
- **規則引擎把關**：根節點的候選著手直接取自 `src/rules/engine.js` 的 `legalMoves()`，回傳的一定是其中之一，電腦不可能下出違規棋步。這個產生器已通過初始局面 1～3 層節點數（30／900／25,470）驗證，並與 python-shogi 比對 1,736 個局面的合法步集合。
- **搜尋專用棋盤**：根節點以下改用 `ai.js` 內部的高速棋盤（13×11 帶牆 mailbox、`Int8Array`、增量走子／還原與 Zobrist 雜湊），不必每一步都複製整個局面。單元測試會確認它在同樣 1,736 個局面產生的合法步與規則引擎完全一致（含二步、打步詰、無處可走的打入）。

### 3.2 搜尋演算法

| 技術 | 說明 |
| --- | --- |
| **Negamax + PVS** | Alpha-Beta 剪枝的主變例搜尋：第一手用完整視窗，其餘先用零寬視窗驗證，比較好才重搜 |
| **迭代加深（Iterative Deepening）** | 從深度 1 開始逐層加深，時間到就停；當層已證實優於前一最佳手的著手也會被採用 |
| **置換表（Transposition Table）** | 以 64 位元 Zobrist 雜湊記住搜過的局面（分數、深度、最佳手），約 100 萬格 |
| **靜止搜尋（Quiescence）** | 深度用完後繼續搜吃子，避免在交換途中下判斷而漏看被吃回（入門不使用） |
| **王手延長** | 被王手時多搜一層，較不會漏看殺棋與脫逃 |
| **空著剪枝（Null Move）** | 形勢已明顯夠好時，讓對方連走一步仍佔優就直接剪枝 |
| **延後著手縮減（LMR）與淺層剪枝** | 排序靠後的平穩著手先減層搜尋；接近葉節點時略過明顯無望的平穩著手（王手、吃子、升變不會被略過） |
| **著手排序** | 置換表最佳手 → 吃子（MVV-LVA）→ 升變 → Killer 著手 → History 分數 |
| **千日手** | 搜尋路徑或本局先前出現過的局面視為和棋（0 分），領先時會主動避開 |
| **將死分數** | 無合法步時回傳 `-100000 + 層數`，越快的將死分數越高，電腦會選最短的殺法；以打步將死的一方判負 |
| **時間控制** | 每 1,024 個節點檢查一次時間；已用掉六成時限就不再開始下一層 |
| **入玉宣言** | 輪到電腦且符合宣言條件時會直接宣言 |

### 3.3 局面評估

評估函式以「輪到的一方」為正向計分：

- **子力價值**：採用職業棋士谷川浩司提出的子力表，以步 = 100 換算：步 100、香 300、桂 400、銀 500、金 600、角 800、飛 1000；成駒為と金 700、成香／成桂／成銀 600、馬 1000、龍 1200。玉不計子力，勝負由將死分數處理。
- **持駒**：以基本價值 ×1.05 計算，反映持駒可以隨處打入的彈性。
- **位置加分**：棋子越往前越加分（步每段 +6，銀桂 +3，成駒 +4 等，金與飛角不加），靠中央的列也會加分。
- **囲い**：金、銀與成駒緊靠己方玉時加分（相鄰 +20～30，距離 2 格減半），讓電腦懂得組圍。
- **玉的危險度**：統計對方在玉周圍 2 格內的攻擊子（相鄰加倍、龍馬最重）與持駒，攻擊量越大扣分越多（隨攻擊量平方成長，上限 14 步分）；玉越往前也扣分（每段 −9）。

### 3.4 棋力設定

| 棋力 | 搜尋 | 思考時限 |
| --- | --- | --- |
| 入門 | 1 層，不做靜止搜尋與王手延長 | 0.2 秒 |
| 中級 | 3 層＋靜止搜尋 | 最多 0.8 秒 |
| 高級 | 迭代加深到時間用完（開局約 10 層、中盤約 6 層） | 約 3 秒 |
| 提示（給玩家用） | 同高級 | 約 1.5 秒 |

設定儲存的棋力代號沿用舊值（入門 1、中級 3、高級 4），原本選「初級」的玩家會改為中級。仍然沒有定跡庫與類神經網路評估，高級是能認真對抗一般業餘玩家的程度，但不是競技用引擎。

## 4. MQTT 連線使用的技術

連線對戰**不需要自架遊戲伺服器**。兩個瀏覽器都連到同一個 MQTT broker，broker 只負責轉送訊息，棋步驗證、計時與勝負判定都在雙方瀏覽器各自完成。

### 4.1 技術組成

| 項目 | 內容 |
| --- | --- |
| 函式庫 | **MQTT.js 5.15.2** 瀏覽器 ES 模組，放在 `vendor/mqtt.esm.js`，不依賴 CDN |
| 協定版本 | **MQTT 5.0** |
| 傳輸層 | **MQTT over WebSocket**（`ws://` 或 `wss://`） |
| 預設 broker | EMQX 公開測試伺服器 `wss://broker.emqx.io:8084/mqtt`，可在「設定 → 進階」改成自己的 broker |
| 訊息格式 | JSON |
| 程式位置 | `src/online/net.js`（`OnlineRoom` 類別）、`src/app.js`（對局同步） |

### 4.2 連線參數

| 參數 | 值 | 目的 |
| --- | --- | --- |
| `clientId` | `sks-` + 12 位隨機十六進位 | 每個分頁一個身分 |
| `clean` | `true` | 不保留舊的連線階段 |
| `keepalive` | 15 秒 | 盡快讓 broker 發現斷線 |
| `reconnectPeriod` | 2.5 秒 | 斷線後自動重連 |
| `connectTimeout` | 8 秒 | 連線逾時 |
| QoS | 全部使用 **QoS 1** | 至少送達一次，搭配手數編號去除重複 |

### 4.3 使用到的 MQTT 功能

| MQTT 功能 | 在遊戲中的用途 |
| --- | --- |
| **主題階層** | 以 `sakurama-shogi/v1/…` 為前綴，依房號分開 |
| **保留訊息（Retained Message）** | 房主把房間資訊保留在 `room/<房號>/info`，加入者一訂閱就能馬上確認房間存在；隨機配對的等待公告也是保留訊息 |
| **萬用字元訂閱（`+`）** | 隨機配對時訂閱 `match/<用時>/+`，一次收到所有正在等待的公告 |
| **訊息到期（Message Expiry Interval，MQTT 5）** | 房間資訊 900 秒（15 分鐘）後自動失效；配對公告只保留 45 秒、每 20 秒重發，當機或關閉的玩家很快就會從配對池消失 |
| **清除保留訊息** | 開局或取消時發布空內容的保留訊息，把房間從 broker 移除 |
| **遺囑訊息（Last Will and Testament）** | 連線時設定遺囑：若異常斷線，broker 會代為發布 `presence/<clientId>` = `offline` |
| **上線狀態（Presence）** | 連上時發布 `online`，雙方訂閱對手的 presence 主題即時得知對手在不在線 |

### 4.4 主題設計

| 主題 | 用途 |
| --- | --- |
| `sakurama-shogi/v1/room/<房號>/info` | 保留訊息：`{ v, host, time, side }` |
| `sakurama-shogi/v1/room/<房號>/msg` | 對局中所有訊息 |
| `sakurama-shogi/v1/presence/<clientId>` | `online`／`offline`（遺囑） |
| `sakurama-shogi/v1/match/<主時間>-<讀秒>/<房號>` | 保留訊息：隨機配對的等待公告 `{ v, host }` |

每則 `msg` 都帶有共同欄位：`v`（協定版本）、`t`（訊息類型）、`from`（發送者 clientId）、`g`（第幾局，用來丟棄上一局殘留的訊息）。收到自己發出的訊息會直接略過。

| 訊息 `t` | 內容 |
| --- | --- |
| `join` | 加入者送出自己的名稱與頭像 |
| `start` | 房主指定對象（`to`）、先後手、用時與雙方資料 |
| `move` | 手數 `n`、著手 `{from, to, drop, promote}`、此手用時、自己的剩餘時間 |
| `resign`／`declare`／`timeout` | 投了／入玉宣言／超時 |
| `hello`／`sync` | 重連後回報自己的手數，對方補送漏掉的棋步、時間與結果 |
| `rematch`／`leave` | 要求再戰／離開房間 |

### 4.5 配對流程

```
房主                          Broker                          加入者
 │ 訂閱 room/X/msg              │                               │
 │ 發布 room/X/info（保留, 15分）│                               │
 │                              │◀── 訂閱 room/X/info ───────────│
 │                              │─── 保留的房間資訊 ────────────▶│
 │                              │◀── 訂閱 room/X/msg ────────────│
 │◀──────────── join（名稱、頭像）───────────────────────────────│
 │ 清除 info、決定先後手         │                               │
 │──────────── start（to=加入者）───────────────────────────────▶│
 │ 訂閱對手 presence             │               訂閱對手 presence │
 ╞═══════════════════ move / resign / … 於 room/X/msg ═══════════╡
```

- **房號**：5 碼，使用 `crypto.getRandomValues` 從 32 個不易混淆的字元（去掉 I、O、0、1）產生，共約 3,355 萬種組合。
- **房間已滿**：加入者收到 `start` 但 `to` 不是自己，就表示房間已經被別人加入。
- **邀請連結**：`#/join/<房號>` 會打開好友對戰並帶入房號，由玩家按「加入」確認。只有網頁不是從 `localhost`／`127.0.0.1` 開啟時才提供分享按鈕，因為這類網址在別台裝置打不開。

### 4.6 隨機配對

隨機配對沒有配對伺服器，而是沿用上面的房間流程，只多一層「公告」：

0. 連線對戰頁先讓玩家選「隨機配對」或「好友對戰」（建立房間／輸入房號），只顯示該路線需要的選項。
1. 按下「開始配對」後訂閱 `match/<用時>/+`，等 1.2 秒收齊所有保留的公告（只和選了相同用時的玩家配對）。
2. 有公告就隨機挑一個，照一般流程加入那個房間（等待回應 5 秒）。房間已滿或沒回應就換下一個。
3. 沒有可加入的公告，就自己開一個房間（先後手隨機），並在 `match/<用時>/<房號>` 發布公告，等別人來加入。有人加入時房主清除公告，照常送出 `start`。
4. **兩人同時開房**：兩個等待中的房主會互相看到對方的公告。規則是房號較大的一方撤掉自己的房間、改去加入房號較小的一方，所以不會兩邊都在等。
5. 取消配對、離開頁面或斷線時，公告會被清除或在 45 秒內到期。某個公告加入失敗後不會再試，除非它之後又重新發布（代表房主還在等）。

### 4.7 可靠性設計

- **雙方各自驗證**：收到的棋步先檢查格式、手番與手數，再交給本機規則引擎；不合法就忽略，所以對方無法送出違規棋步。
- **防重複與亂序**：每手附上手數 `n`。重複的舊手數直接略過；若手數跳號，就送 `hello` 要求對方用 `sync` 補齊。
- **斷線重連**：MQTT.js 會自動重連；重連成功後送出 `hello`，對方把漏掉的棋步、時鐘與結果一次補送過來。
- **對手斷線**：透過遺囑訊息得知對手離線，畫面顯示倒數，**60 秒內沒回來即判勝**；回來則繼續對局。
- **計時同步**：各方以自己的時鐘為準，每手附上剩餘時間。對手已經超時卻沒回報時，等 15 秒後判定超時勝。

### 4.8 安全性注意事項

預設的公開 broker 任何人都能訂閱主題，名稱、頭像與棋步都以明文 JSON 傳送，**只適合休閒對局**。若要私下使用，建議自架 broker（例如 EMQX、Mosquitto 開啟 WebSocket），並在設定中改成自己的 `wss://` 位址。
